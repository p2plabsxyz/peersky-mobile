# PeerTunes (mobile)

PeerSky Mobile ships PeerTunes, the iPod style player for local and `hyper://` music, as a built-in app at `peersky://p2p/peertunes/`. The app itself is the static web app from [p2plabsxyz/peertunes](https://github.com/p2plabsxyz/peertunes), vendored unmodified. The Bare runtime serves it from a loopback HTTP server and proxies its `hyper://` reads, because a WebView page cannot fetch `hyper://` on its own.

## How the app gets its files

- `assets/peertunes/` is the vendored copy of the app. `manifest.json` records the upstream commit it was taken from.
- `scripts/generate-peertunes-runtime.mjs` turns those files into `backend/peertunes/peertunes-runtime.mjs`, which is committed and regenerated by `npm run bundle:bare`, the same way the Yjs and KaTeX runtimes are handled.
- `backend/peertunes/server.mjs` serves the files on `127.0.0.1` and injects a one line bridge into `index.html`:

```js
window.peerskyHyperAsset = (url) => '/hyper/asset?url=' + encodeURIComponent(url)
```

PeerTunes checks for that global and routes folder listings, tag reads and audio playback through it. The path is relative, so the page never sees a proxy token.

To update the app, replace the files under `assets/peertunes/`, update `manifest.json`, and run `npm run generate:peertunes-runtime`.

## Endpoints

| Endpoint | Method | Purpose |
|---|---|---|
| `/` and bundled files | `GET`, `HEAD` | The app page, scripts, styles and icons |
| `/hyper/asset?url=hyper://...` | `GET`, `HEAD` | Streams a file from a drive with `Range` support. With `Accept: application/json` it returns the folder listing instead |

Everything else answers `404`, and any write method answers `405`. PeerTunes probes for a writable drive when publishing a share; the `405` makes it show its "publishing needs desktop PeerSky" message, since mobile drives are read-only.

## Runtime flow

1. Opening `peersky://p2p/peertunes/` sends `RPC_PEERTUNES_START` to the Bare worklet.
2. The backend starts the loopback server on the fixed port `47317` and falls back to a random port if that one is taken.
3. React Native opens the local URL in a WebView. A share link such as `peersky://p2p/peertunes/#playlist=hyper%3A%2F%2F...` passes its fragment through, so the app can offer to import or play the playlist.
4. Inside the page, `hyper://` reads go to `/hyper/asset`, which uses the read-only Hyper fetch from `backend/hyper/fetch.mjs`.

The port is fixed on purpose. The WebView origin is `host:port`, and the music library lives in that origin's IndexedDB, so a stable port is what keeps the library between launches. When the fallback port is used the app still works, but that session's library does not carry over.

## Sources the player can load

| Source | Works on mobile | Notes |
|---|---|---|
| `hyper://` | Yes | Proxied through `/hyper/asset`. LAN peers are found without internet, see below |
| `http(s)://` | Yes | Fetched by the page directly, so the server must send CORS headers |
| `ipfs://` and `ipns://` | No | The mobile Bare runtime carries no IPFS node. Desktop PeerSky does |
| Files picked from the device | Yes | Held in the WebView origin's IndexedDB |

`ipfs://` links fail with a message naming the scheme rather than a generic error, so the limitation is visible rather than puzzling.

## Playing without internet

LAN discovery is wired into the shared Hyper SDK in `backend/hyper/runtime.mjs`, not into any one app, so PeerTunes inherits it. With `@p2plabs/hyperdht-mdns` a drive seeded by a peer on the same network resolves and streams with no internet at all. Music that must survive leaving the network needs the folder retained through **Keep offline**, as described in [Hyper](hyper.md).

## Background playback

PeerTunes plays through its WebView. iOS declares the `audio` background mode in `app.json`, so playback continues when PeerSky leaves the foreground. Android's WebView keeps playing on its own, so the app declares no media playback service there (`expo-audio` runs with `enableBackgroundPlayback: false`, and the permission is blocked). The page publishes track, artist, album and artwork through the Media Session API, which is what the system player shows.

## Safety notes

- The server binds to loopback only, the same as the P2PMD and Hyper asset servers.
- Only bundled files resolve. Dot segments, backslashes and bad encoding are rejected before lookup.
- `/hyper/asset` validates the URL with `parseHyperUrl` before any network work.
- The WebView only navigates within its own origin. Links to other sites, such as the GitHub link in About, open in the browser instead.
- Android cleartext HTTP stays scoped to localhost through the existing network security config.

## Test coverage

- `test/protocol/peertunes-http.test.mjs` covers the endpoint contract with an injectable Node HTTP server and a fake Hyper fetch: bridge injection, content types, path rejection, write rejection, URL validation, JSON listings, and range streaming.
- `test/platform/internal-apps-registry.test.mjs` covers the `peersky://p2p/peertunes/` route, share link matching, and the WebView origin guard.
